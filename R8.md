## Why each planner decision does not hold (BLOCKED-D5)

### D5-a: P3 has no allowed route

The planner's default declares `onFail: {raise: "queue.change", then: "retry"}` on the `confirm` step. `schemas/loop-version.json` limits `steps[].onFail.raise` to `["queue.fix", "queue.clarify"]`, and `LoopStep.onFail.raise` in `src/records/types.ts` has the same union. The packet forbids schema enum changes.

At base the runner takes no declined-confirm route. In `humanStep`, a rejected `queue.approve` reverts the pin and stops the run with exit 0, so no entry is opened.

One existing step does open a change: the `create-candidates` agent step of loop.create. `stepRaises` accepts a new `producer/queue.change/entries/<id>.json` the step raised, and `waitOnRaised` parks the run on it with `then: retry`. Declaring that would mean adding `producer/queue.change/entries/*` to the standard step's `writes`. But `standardOwnWrites` feeds both `undeclaredWrites` and `agentStepWriteIssue`. So the declaration widens the agent write allowlist: an agent step could then rewrite an existing change entry, not only raise a new one. Changing that is forbidden ("allowlists").

Options:
1. **(default)** Owner-approve adding `queue.change` to the `onFail.raise` enum in the loop-version schema and in the `LoopStep` type. Then add the minimal runner branch: in `humanStep`, a declined `queue.approve` on a step whose `onFail.raise` is `queue.change` opens the owner's change on the slot through `raiseFeedback`, using the answer's quote as the words. The run then waits on that change with `then: retry`; `readRetry` already handles `queue.change#` entries. Declare it on `confirm` in loop.fill, loop.refine and loop.choose, with a runner test.
2. Declare the write on the loop.create `create` step. Pair it with a runner guard that makes `queue.change` entries create-only, the way `queue-slot` already is. This is an allowlist change.
3. Accept P3 red until a later unit; the check change for that is forbidden here.

### D5-b: P4 changes content-agent cells

The agent loops (loop.scope, loop.slot, loop.create, loop.choose) must keep the standard's failure routes exactly (`loopExtensionIssues`: "changes its failure route"). Every content agent's own v1 of those loops has no `onFail` on the newly routed steps. So the standard-only edit turned publisher W2 red and added 9 rows to director, designer and writer W2. It also failed 16 `agent package loop candidates` tests.

The new `onFail`s also change runner behaviour that tests pin:
- a failed release `pin` or agent `pick` now waits on a clarify with exit 0, where it used to stop with exit 1 (flows B3 tests);
- subjectless loop.scope runs stop with "no clarify entry could be raised".

Options:
1. **(default)** Extend R8's scope to mirror the same `onFail`s into each content agent's v1 of loop.scope, loop.slot, loop.create and loop.choose (16 files, none hash-pinned). Then retarget the flows and agent-loops tests that pin the stop-on-failure exits.
2. Route only the dead ends in Producer-only loops (loop.fill, loop.refine, loop.release, loop.audit), and leave the agent-loop steps for a unit that owns the agent packages. P4 would stay red with 15 rows.

### D5-c: the required conform test is under a forbidden path

`src/conform/producer.test.ts` is required to exit 0. It pins today's known reds: P1/P3 `queue.change` rows, and a `world()` that filters `queue.change` out of the queue kinds. With queue.change placed, it fails 10 of 16 tests ("queue.change is not a queue slot"). It sits under `packages/producer/src/conform/**`, which the packet forbids touching.
